# 配置 worktree-env

目标：根据项目的真实启动方式，在仓库外配置 wte，让同一仓库的多个 worktree 获得可运行的本地环境。优先保留项目代码、启动命令和团队配置，通过用户级 Profile 完成适配。

先阅读 [配置参考](references/configuration.md)。参考按 worktree-env 0.6.0 源码核对；实际操作以用户已安装版本的 CLI、模板和实现为准。不要假设当前工作目录就是 worktree-env 源码或用户的目标项目。

## 0. 落实已授权的前置动作

- 先提取用户当前明确要求立即执行的动作及范围，区分它与尚待批准的配置方案；用户提供的历史记录、示例或待评审报告本身不是执行授权。
- 用户明确要求“先暂停 Monitor”等可独立执行的前置动作时，只做定位可执行程序、有效配置目录及作用范围所需的最小检查，然后执行并核实，不把它推迟到完整方案审批。如果范围含糊或发现指令未涵盖的风险，先说明并询问；已有同范围授权无需重复确认。
- 暂停 Monitor 使用 `wte monitor disable`，说明这是该宿主机 wte 监控的操作，会影响其他受监控项目，Hooks 保留。结合命令结果及 `wte doctor` 的 Monitor 状态核实；doctor 因其他配置错误提前退出时，查平台监控注册/活动状态，不能仅凭退出码推断暂停成功。失败或无法核实时如实报告，暂停依赖该状态的后续写操作。
- 将动作标记为“已执行并验证 / 执行失败 / 尚待批准”，先向用户反馈真实状态，再进入只读发现。已经暂停就不再写“尚未做任何变更”，也不重复安排暂停。
- 暂停授权不包含恢复、发布 Profile、迁移文件或重启服务；这些动作按各自范围确认。用户未批准恢复时保持暂停并在交付中注明。

## 1. 只读发现

先自行查明能从本机和项目得到的信息，只询问阻塞方案的未知项。

### 主机与现有配置

- 确认目标仓库路径；未提供且当前目录含糊时先问。
- 检查系统、`git --version`、`command -v wte`、`wte --version`、`wte --help`；缺少 wte 时检查 `uv`，先提出安装计划。
- 解析配置根目录：非空 `WTE_CONFIG_HOME` → 非空 `XDG_CONFIG_HOME` 下的 `wte/` → `~/.config/wte/`。展开路径并在后续命令中保持同一配置环境。
- 列出现有 Profile 文件，定向阅读目标项目 Profile、`config.yaml` 和已安装模板。不要批量输出其他项目的私有配置。
- 在目标仓库中检查 Hooks 来源：
  ```bash
  git config --global --show-origin --get-all core.hooksPath
  git config --show-origin --show-scope --get-all core.hooksPath
  ```
  未设置时退出码 1 属正常情况。第二条用于识别仓库、worktree、include 等配置覆盖。
- 已安装 wte 时运行 `wte doctor`、`wte list`，记录 Hooks、Monitor、分配状态；输出如含私密内容先脱敏。
- 全局 hooksPath 指向其他管理器时，先解释冲突并询问整合方案。不能直接 unset 或覆盖。仓库级 hooksPath 可能绕过全局分发器；原生 `.git/hooks` 的链式调用不等于支持任意 Hooks 管理器。

### 仓库与配置入口

在目标仓库中执行只读 Git 命令：

```bash
git rev-parse --show-toplevel
git rev-parse --git-common-dir
git worktree list --porcelain
git status --short
```

- 确认 main worktree 的真实路径；当前目录可能是 linked worktree。常规仓库的 common Git 目录是主工作树的 `.git`，特殊布局结合 porcelain 列表核实。bare 仓库等不明确布局先确认版本支持，不能把任意 linked worktree 填成 main。
- 定向阅读项目说明、包清单、锁文件、启动脚本、框架配置、环境文件示例、Compose 配置等。主动发现仓库内已有的本机配置文件（如 `.env`、服务私有配置、证书），包括被忽略的文件；仅按已知配置入口定向检查，不全仓库搜索 Secrets 或输出真实值，通常只需要变量名、文件路径和加载逻辑。
- 对发现的文件记录 Git 跟踪/忽略状态、普通文件/软链接类型、实际来源和使用它的服务，分类为：保留在仓库的团队配置、适合迁出并共享的本机配置、按 worktree 生成的动态配置。存在迁移候选时必须阅读并执行 [本机配置迁移流程](references/migration.md)，不能要求用户先自行搬好文件再配置 wte。
- 列出实际需要并行运行的服务：监听端口、前后端访问 URL、代理、CORS、WebSocket、HMR、调试端口、容器宿主机映射等。
- 每个端口都要找到真实配置入口，说明依据的文件路径。不能仅凭框架名称猜测环境变量有效。例如 `VITE_PORT` 不是 Vite 自动采用的监听端口，需要启动配置显式读取；Python 服务也未必读取 `PORT` 或 `.env.development`。
- 确认环境文件加载顺序、启动模式，以及已导出的 shell 变量/命令行参数是否覆盖文件。共享 Secrets 与生成端口文件必须能被应用一起加载，且动态端口最终生效。
- 分清可共享服务与需隔离的实例：wte 分配端口不等于自动隔离数据库数据、Docker 容器名/卷或启动服务。如果现有项目没有可用的本地配置入口，说明限制，给出最小改动建议并单独征求批准。

### 按 worktree 检查实际影响范围

- 结合 `git worktree list --porcelain`、注册表及已安装版本确定受影响范围，分别列出当前、主工作树和其他 linked worktree。Monitor 可能处理未注册的主工作树；已注册 worktree 仍可能被 checkout Hook 或显式 sync 重新投影，不能因已注册就忽略长期风险。
- 为每个受影响 worktree 建立检查表：路径、注册状态、触发方式、所需代码/加载入口是否存在、每个投影目标的存在/类型/跟踪/忽略/父目录状态、本机配置差异、预期变更、是否已检查及是否已批准。逐个在对应 worktree 执行检查，不能用当前分支的结果替代。
- 没有目标服务代码也可能被创建目录和配置；分支间 `.gitignore`、tracked 文件和配置内容可能不同。未经核实，不宣称其他 worktree“无覆盖风险”或“已忽略”。Monitor 恢复也可能处理其他已配置项目的待投影 worktree；无法核实或批准的范围须明确列为阻塞项。
- 影响范围无法检查或存在冲突时，经批准暂停或保持 Monitor 暂停，重新设计/缩小方案；不要发布可能由 Hooks 触发的不安全 Profile。0.6.0 的 `main-worktree` 匹配覆盖同一仓库，不能通过“只在当前执行 sync”把 Profile 变成当前 worktree 专用，也不能虚构分支过滤字段。

## 2. 设计并展示草案

展示以下内容，仅对尚未获批的动作询问一次明确批准；缺少必要信息时保留草案，不发布激活文件。

1. **检测结论**：目标 main worktree、有效配置目录、wte 版本、Hooks/Monitor 情况、配置入口及依据。
2. **端口与文件映射**：服务 → port id → 监听配置及引用它的 URL；已有配置的分类与处置。分开列出两张表：①一次性迁移：指定 worktree 的原路径 → 外部源 → 本次建立的链接；②长期投影：Profile source/body → target → 适用 worktree → 使用它的启动入口。标出原路径是否由 Profile 管理、哪些手动链接不会在后续 worktree 自动重建；路径不同时解释原因并确认预期启动方式。默认迁移目录为 `<config-home>/secrets/<project>/`，保留仓库内相对路径以区分同名文件；优先复用已核实的外部安全来源。
3. **配置草案**：完整的新 Profile 或现有 Profile 的精确 diff。使用规范的连字符键，沿用现有 name、文件名、port id，避免不必要的重分配。只配置需要的能力。
4. **执行清单**：已完成动作及核实结果；尚待执行的安装/升级、`wte init`、Profile 路径、覆盖/替换目标、备份、Git 本地排除规则、准备同步的 worktree、初始化命令、Monitor 目标状态和验证命令。若需启动代码适配，单独列出代码 diff/改动范围及批准项。
5. **副作用与回退**：全局 hooksPath 的影响；目标文件整文件覆盖/替换；后台初始化的网络访问及依赖安装脚本；逐 worktree 检查表中的自动投影范围、差异和阻塞项。明确后续新 worktree 的启动前提：所基于的代码必须包含所需适配，不能把当前分支未提交或未合入的改动当作所有分支已有能力。

### 草案的硬约束

- Profile 使用仓库外的配置根目录下 `<project>.yaml`；不要默认在仓库添加脚本、AGENTS.md、CLAUDE.md 或修改团队 `.gitignore`。
- 活跃目录根部的 `.yaml`、`.yml`、`.json` 会被扫描。草稿和备份放目录外，或使用不被加载的最终后缀（例如 `.yaml.draft`、`.yaml.bak`）。不要复制为 `backup.yaml`。
- **启用 Monitor 时，写入/重命名/删除 Profile 就可能触发执行，不必等到 `wte sync`。** 草案阶段不改活跃配置，也不通过创建测试 worktree 间接触发 Hooks。
- 每个目标必须是 worktree 内相对路径，不含 `..`；检查父目录软链接是否越界，检查目标是否已存在、为目录/软链接、被 Git 跟踪或被忽略。`link-files` 与 `write-files` 不能使用相同或互相嵌套冲突的目标。
- `write-files` 是完整文件生成，不是合并；`link-files` 会删除已有文件/软链接后重建链接。已存在目标必须先说明如何保存原文件或链接信息；tracked 目标默认不投影。
- 迁移按“先复制到仓库外、静默校验内容一致、保留回退备份、再替换为软链接”执行，不先删除或直接搬走唯一原件。外部目标已存在时不得覆盖；内容相同可经确认复用，不同则停止并让用户选择来源或新路径。
- Secrets 源在投影前必须存在且是仓库外文件；优先使用用户已有的安全来源。只向用户展示路径、权限、类型和一致性结论，不把值放进聊天、Profile、注册表、提交或日志；复制与内容比对在本机完成。源不能是即将被替换的目标自身，备份也必须保存在仓库外的私有目录。
- 用 `git ls-files -- <target>` 检查跟踪状态，用 `git check-ignore -v -- <target>` 检查排除。必要时经批准写入 Git common directory 的 `info/exclude`，不修改团队规则；忽略规则不能保护已跟踪文件。
- 默认不加入 `setup-commands`。需要时按锁文件和包管理器选择命令，设置合适的 `cwd`、`skip-if` 并让用户批准。依赖安装可能执行第三方代码；不自动添加数据库迁移、破坏性清理或长期运行的服务。
- Monitor 按需启用，适用于沙箱/IDE 创建 worktree 时 Hook 无法工作；不是每次配置的必选项。

## 3. 批准后应用

仅执行获批清单；范围、覆盖对象或命令发生变化时重新确认。

1. 重新检查配置和文件状态，避免覆盖用户在草案之后的修改。保存必要备份；私有配置文件建议权限 `0600`，私有目录 `0700`。
2. 若需要，执行 `uv tool install worktree-env`；升级用 `uv tool upgrade worktree-env`。不在项目中添加 Python 依赖，不擅自从当前源码安装开发版。
3. 若批准安装/刷新 Hooks，执行 `wte init`。冲突时停止，不能用清除原配置来强行绕过。自定义配置目录还需确认终端、GUI Git、Monitor 获得一致的环境。
4. 在任何迁移、替换或激活前复查逐 worktree 检查表和自动触发风险；若 Monitor 已启用且影响范围无法控制，执行已授权的暂停或先征求批准，核实状态并记录恢复条件；已暂停则保持，不重复执行。避免同时运行 checkout、sync 或修改活跃 Profile；无法排除并发写入时停止。按迁移流程准备批准的外部源、私有备份和本地排除规则，静默校验复制结果；完成 YAML、模板占位符和目标冲突检查。只在原件已安全保存后，由获批的 sync 或明确列入计划的软链接替换完成迁移。
5. 将获批 Profile 先写到非加载后缀的临时文件，校验后原子替换到最终路径；不修改 wte 的 `state/`，不在活跃文件中边写边试。
6. 运行 `wte doctor`。区分错误和警告：未启用可选 Monitor 可以接受，缺失 Secrets 或错误匹配不能忽略。失败时停止后续同步并报告；Profile 发布本身已可能触发 Monitor，不宣称这一步是无副作用预检。
7. 只在批准的 worktree 中执行 `wte sync`。它分配端口、覆盖文件并自动启动配置的初始化命令，没有假定的 `--dry-run` 或 `--no-setup` 选项。不要遍历同步所有 worktree。
8. 仅在启用/恢复已获批、最新逐 worktree 检查表无阻塞项且自动投影范围未变化时，执行 `wte monitor enable` 并核实状态。新增 worktree、目标变动或未检查项需补查，范围扩大则重新确认；否则保持暂停。Profile 更新通常会自动刷新监听，但已注册 worktree 的文件更新仍需按范围显式 sync；以当前版本行为为准。

## 4. 验收与交付

- `wte doctor` 检查结构、Secrets 路径和集成状态；`wte list` 核对目标 worktree 和 port id 的分配。doctor 通过不代表应用真的使用了端口，也不保证后台初始化成功。
- 核对外部源与迁移前文件内容一致、源/备份权限、软链接目的地及原路径可读性；检查生成文件非敏感端口字段、Git 忽略与 `git status --short`，确保无意外跟踪文件变更或 Secrets 暴露。迁移清单逐项标注已完成、未替换或已恢复；备份保留位置和清理时机交给用户确认。
- 初始化是异步的：检查进程/完成标记和日志中的必要脱敏片段，不把“已启动”说成“已完成”。`skip-if` 存在也未必表示上次安装成功。
- 验证配置加载优先级：共享文件、原配置回退、生成端口文件、进程环境及 CLI 参数谁覆盖谁；用非敏感字段核实最终生效端口，迁出配置的相对路径/包含文件仍可解析。涉及代码适配时，在隔离测试环境验证缺少 wte 配置时原启动回退仍有效，不临时删除真实 Secrets 来测试。
- 经批准启动服务，验证监听端口、前后端连通、代理/CORS、适用的 HMR/子应用 URL 等。分别说明当前工作树的一次性链接是否可用，以及后续 worktree 仅依靠 Profile 和相应代码是否具备预期启动条件；不能用前者代替后者。需要创建第二个 worktree 测试时，事先批准路径、代码基线和清理方式；未运行或未覆盖的场景标记为未验证。
- 最终简洁列出：实际变更路径、一次性迁移与长期投影两类结果、Profile 名、已验证的 worktree/端口、Hooks/Monitor 的实际状态、未完成项及下一步。
- 回退按实际变更处理：先控制自动触发，经批准停用 Monitor/移出 Profile，再按迁移流程确认文件未被继续修改、恢复目标备份和本地排除规则；删除 Profile 或 `wte uninstall` 不会自动恢复已生成文件/Secrets 链接，也不会停止已启动的初始化进程。`wte uninstall` 影响所有项目的 Hooks 和 Monitor，不把它作为单项目回退默认操作。
