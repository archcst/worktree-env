# 仓库内本机配置的迁移流程

适用于用户已拥有仓库，且本机配置仍在其中的情况。Agent 主动发现、制定方案并在批准后完成迁移，保持应用使用的原路径。迁移只改变本机文件布局，不默认修改团队版本化配置。

## 1. 发现与分类

根据启动脚本、配置加载代码、文档及示例定位真实配置文件；定向检查被忽略的 `.env`、本机 YAML/JSON、证书等。默认文件列表/搜索可能漏掉 ignored 文件，不能据此认定配置不存在。不要广泛扫描用户目录或输出配置值。

对每个候选检查：

- `git ls-files -- <target>`：是否已跟踪；`git check-ignore -v -- <target>`：是否被忽略。此处 `<target>` 是仓库根目录相对路径，命令在该仓库内执行。
- 文件类型、大小、权限；用不跟随最终软链接的检查区分普通文件、链接、目录及悬空链接。
- 谁加载它、加载顺序、相对路径的解析基准、哪些字段需要随 worktree 变化。
- 按主流程的逐 worktree 检查表，在每个实际受影响 worktree 核实配置差异、目标文件与忽略规则；包括 Monitor 可能处理的未注册主工作树。只对任务范围内的同名文件做静默内容比对，内容不同不能擅自选某个 worktree 的版本覆盖其他版本。无法检查的目标列为阻塞项，不发布或恢复可能触达它的不安全自动投影。

| 分类 | 默认处置 |
| --- | --- |
| Git 已跟踪的团队配置、示例文件 | 保留；优先寻找项目已有的 ignored 本地覆盖入口 |
| 未跟踪的本机私有/共享配置 | 迁移候选；检查并补齐本地排除规则 |
| 包含端口、URL 等动态值的配置 | 确认可否用独立本地文件覆盖；共享部分链接，动态部分生成 |
| 已链接到仓库外安全文件 | 核实后复用既有 source，无需再复制；不擅自更改外部源权限或内容 |
| 指向仓库内文件的链接、悬空链接、目录或特殊文件 | 单独确认来源和处理方案，不按普通文件直接迁移 |

多个 worktree 的本机值如果有意不同，单一共享 source 就不合适；说明 Profile 表达能力和隔离需求，先解决方案再迁移。发现已跟踪 Secrets 时提醒其可能已进入 Git 历史；迁出或忽略并不能消除历史暴露，不擅自重写历史。

## 2. 明确迁移映射并审批

默认外部源位置：

```text
<config-home>/secrets/<project>/<仓库内相对路径>
```

`<config-home>` 使用实际 wte 配置根目录，`<project>` 使用唯一、安全的项目目录名，不含路径分隔符或 `..`。保留相对目录，避免 monorepo 中多个 `.env` 重名。确认实际目录在所有相关 worktree 外，不在 wte `state/` 中，也不会因软链接解析回仓库内。若用户自定义的配置根目录在仓库内，先为 Secrets 选择并批准真正的外部目录。

例如：

| 原路径 | 外部源 | 链接回的位置 |
| --- | --- | --- |
| `/code/my-app/apps/api/.env` | `~/.config/wte/secrets/my-app/apps/api/.env` | `/code/my-app/apps/api/.env` |
| `/code/my-app/apps/web/.env` | `~/.config/wte/secrets/my-app/apps/web/.env` | `/code/my-app/apps/web/.env` |

此例中 Profile 的 `link-files.source` 指向外部源，`target` 仍为 `apps/api/.env` 或 `apps/web/.env`，因此后续匹配的 worktree 也会在这些相对路径建立链接。外部目录为本机文件存储约定，并非 wte 自动迁移功能；复制和原件保护由 Agent 完成。

### 一次性迁移与长期投影分开描述

草案必须包含两张表，而不是只展示外部源路径：

| 表 | 必填信息 |
| --- | --- |
| 一次性迁移 | 指定 worktree、原路径、外部源、本次替换后的路径、手动操作或由 Profile 执行、备份 |
| 长期投影 | Profile 的 source/body、target、适用 worktree、实际读取它的启动入口、所需代码基线 |

每个一次性原路径都标记是否出现在 `link-files.target` 中。若迁移保留 `apps/api/.env`，但 Profile 将同一 source 投影到 `apps/web/.local/api.env`，则前者的手动链接只存在于本次操作的 worktree，后续 worktree 不会自动得到它。两种路径可以并存，但必须解释用途并取得用户对启动范围的确认：例如仅支持 web 的 launcher，还是也要求直接启动 api。

不能把当前分支的手动链接、未提交启动适配或尚未合入其他分支的代码视为未来 worktree 的固有能力。若预期启动还依赖这些内容，应完善获批方案或明确阻塞项；不能仅凭当前 worktree 启动成功宣称后续自动就绪。

在整体配置草案里一并展示：文件分类、上述两张表、覆盖及复用策略、备份目录、本地 Git 排除规则、逐 worktree 检查结果、动态值处理、执行方式和失败恢复步骤。已经明确授权并核实完成的前置动作单列；仅对剩余未获批动作请求批准，不另外默认扩大迁移范围。

## 3. 先复制、校验，再替换

按每个文件维护状态：`待复制 → 外部副本已校验 → 原件已备份 → 原路径已链接 → 已验收`。仅记录路径及状态，不记录配置内容。

### A. 准备与控制触发

- 复查原路径、类型、Git 状态、修改状态以及目标父目录的真实路径，与获批方案不符时停止。
- 在修改前处理现有 Monitor 和 Hooks 的并发风险。用户已明确要求先暂停 Monitor 时按主流程立即执行并核实，无需等整个迁移方案批准；没有授权则先询问，已暂停不重复安排。恢复是独立动作，须有授权且逐 worktree 检查无阻塞项。迁移准备期间不触发 checkout/sync 或发布未准备好的 Profile。
- 创建专用私有目录，目录权限 `0700`，普通配置文件权限 `0600`；使用 `umask 077` 或等效文件 API，从创建时保护副本和备份。若服务确需不同权限，先确认最小权限方案；设置失败时不能宣称安全准备完成。
- 为源和外部目标做真实路径与文件身份检查，不能是同一文件、硬链接别名，或互相指向的软链接。外部目标及其父目录含可疑链接时停止核实。
- 备份默认使用 `<config-home>/backups/<project>/<唯一批次>/<相对路径>`，同样确认在仓库外；唯一批次不能覆盖旧备份。链接原件记录链接文本，普通原件保存独立副本。

### B. 安全复制与一致性检查

- 原件保持不动，先复制到外部目标目录中的唯一临时文件；使用不覆盖已有文件的创建方式，并在复制过程中保持私有权限。
- 在本机用字节比较（如 `cmp -s`）或程序内部摘要比较，输出仅为“一致/不一致”，不回传内容、diff 或摘要。复制失败、来源发生变化或校验不一致时停止，保留原件。
- 外部正式目标不存在时，以不会覆盖并发新建文件的方式发布校验副本；普通可覆盖的 rename/mv 不能当作无覆盖保证。实现不具备安全发布能力时先停止，不强行覆盖。
- 正式目标已存在：静默比较。相同则按已批准的复用策略使用；不同则保留双方原样，要求用户选择另一个路径或确定正确来源。不要自动合并 Secrets。
- 再复制一份独立回退备份并校验，保留原权限等必要恢复信息。不能只把将被所有 worktree 共享修改的外部源当作唯一备份。

### C. 原路径切换

- 检查批准的 Git 本地排除规则已生效，目标未被跟踪，生成文件目标不会覆盖该共享文件。
- 切换前再次静默比对原件、已校验外部源与备份；发现变化时停止重新确认。不能覆盖迁移期间用户或进程的新内容。
- 所有批准文件的源和备份准备好后，才发布 Profile 并在批准范围内 `wte sync`；只有列入 `link-files.target` 的路径由它替换。Profile target 与一次性迁移原路径不同时，原路径链接按获批清单单独建立，不能把 sync 成功当作该原路径已迁移。同步含其他投影/初始化副作用，须在执行清单中列明。
- 若计划仅先迁移文件，或一次性原路径未由 Profile 管理，可在批准清单内直接替换为链接：先在原路径同目录创建唯一临时软链接，再原子替换原文件，避免删除后创建的空窗；必须先有校验通过的外部副本和独立备份。此方式不更新端口注册表，也不表示 wte 已验证。
- 对每个目标按获批方案选择切换方式，不对同一路径反复替换。多文件迁移不是全局原子操作；中途失败立即停止，逐项记录当前状态，不能声称全部成功。

## 4. 动态配置处理

迁移先保持原文件字节不变。若 `.env` 同时包含 Secrets 和固定端口，优先链接完整文件，再利用项目已支持且优先级正确的本地覆盖文件生成 worktree 独立端口/URL。先验证该组合确实生效，不因为文件名看起来合理就使用。

需要移除或改写共享文件中的动态字段时，单独列出变量名和规则并获得批准；只在本机做有针对性的编辑、保护其他内容，不把 Secrets 写进 `write-files.body`。如果项目只支持单个文件且无法表达共享与动态值的组合，说明限制并提出最小适配建议，不静默丢字段或改启动方式。

配置迁出后还要检查相对路径和包含文件语义：有些加载器按软链接解析后的真实文件目录寻找证书/其他配置。只保持链接路径不保证行为完全一致，必须核实；需要迁移额外依赖或改路径时重新纳入方案批准。

## 5. 验收、保留与恢复

- 确认外部源内容与迁移基线一致（获批编辑除外）、权限正确，原路径是指向预期源的链接且可读；备份存在并通过一致性检查。
- 确认 Profile source/target 正确、生成文件加载优先级正确、所有目标被忽略，`git status --short` 无意外跟踪文件变化。
- 分别检查一次性原路径与长期 Profile target，验证预期的启动入口、加载优先级、进程环境覆盖和迁出后的相对路径语义。需代码适配时，用隔离测试验证无 wte 配置时的回退；后续 worktree 的验收明确所需代码基线，不依赖当前 worktree 的手动文件。
- 其他 worktree 仅在明确批准时同步或创建测试，不能为验收覆盖其不同的本机配置。没有真实启动验证的路径/模式明确标记未验证；恢复 Monitor 前重新核实自动投影范围，不能因当前工作树验证成功就忽略其他检查项。
- 告知用户：通过任一 worktree 修改链接文件会修改所有引用它的 worktree 的共享源；独立值应放生成/本地覆盖文件。不要启动长期写入共享配置的任务而未说明风险。
- 交付逐项迁移结果、外部源和备份路径、未验证项；备份保留到用户确认后再按批准清理，不默认删除。
- 失败后停止自动触发和后续同步，先检查目标是否仍为本次创建的链接/文件、外部源是否又被修改。没有新修改时可按已批准的恢复方案从备份还原普通文件/原链接和原权限；有新修改时保留当前内容与备份，询问取舍，不能直接覆盖。
- 恢复前经批准停用/恢复相关 Profile 规则，避免下一次 Hook/Monitor 又覆盖回去；暂停 Monitor 本身不阻止显式 sync 或 checkout Hook。保留外部源直到确认没有其他 worktree/Profile 使用它；不要将全局 `wte uninstall` 当作单文件恢复手段。
